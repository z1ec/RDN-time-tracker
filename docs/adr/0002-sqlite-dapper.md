# ADR-0002: SQLite + Dapper для хранения данных
- Статус: принято · Дата: 2026-11-09

## Контекст
Данные — несколько тысяч записей за годы работы одного человека, настройки и резервные копии. Требования: изменения сразу на диске (F4.1), устойчивость к сбоям питания и падениям, быстрые выборки по датам для статистики, миграции схемы, работа без установки чего-либо и без прав администратора.

## Решение
- **SQLite** через `Microsoft.Data.Sqlite` (нативная библиотека `e_sqlite3` из `SQLitePCLRaw.bundle_e_sqlite3` упаковывается в single-file exe).
- **Dapper** для маппинга запросов на строки; SQL пишется явно в `EntryRepository`/`SettingsStore`.
- Режим WAL, внешние ключи, `busy_timeout`; каждая операция — отдельная транзакция.
- Миграции — нумерованные SQL-скрипты, встроенные в сборку (F4.4).
- Резервные копии — штатный Backup API SQLite (F4.5).

## Рассмотренные альтернативы
- **EF Core** — миграции и LINQ «из коробки», но тяжёлая зависимость и рефлексия ради двух таблиц; хуже контроль над SQL и временем старта.
- **JSON-файл** — просто, но запись всего файла на каждое изменение, риск порчи при сбое во время записи, нет транзакций и индексов.
- **LiteDB** — встраиваемая документная БД, но меньше экосистема и инструменты для ручной диагностики, чем у SQLite.

## Последствия
- ➕ Один файл, ACID-транзакции, WAL переживает падения; файл можно открыть любым SQLite-браузером.
- ➕ Быстрые выборки по `work_date` (частичный индекс по неудалённым записям).
- ➖ `LOWER`/`LIKE` не понимают регистр кириллицы → поиск фильтруется в C# (F6.4, см. DATA_MODEL.md).
- ➖ `Microsoft.Data.Sqlite` выполняет «асинхронные» методы синхронно → вся работа с БД уходит в пул потоков (`SqliteConnectionFactory.RunAsync`).
- ⚠️ Нативная библиотека в single-file — риск, который проверяется self-test настоящего exe в CI (ADR-0006).
