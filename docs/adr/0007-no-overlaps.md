# ADR-0007: Запрет пересечений записей
- Статус: принято · Дата: 2026-11-09

## Контекст
Если две записи пересекаются, одно и то же время считается дважды и вся статистика (итого, норма, переработка) становится неверной. Чаще всего пересечение — это опечатка или повторная вставка тех же строк.

## Решение
- Новая или изменённая запись не может пересекаться с существующими (F7.1). Проверка — в `EntryValidator` (Core), вызывается из `EntryService` для быстрого ввода, формы и редактирования.
- Сравнение в **абсолютных минутах** с учётом соседних дней: из БД берутся записи с датами `[дата − 1; дата + 1]` (запись не длиннее 24 ч, поэтому дальше пересечений быть не может).
- **Касание** (`конец == начало`) допустимо.
- При редактировании запись не сравнивается сама с собой.
- При многострочной вставке строки проверяются и с базой, и между собой; при любой ошибке не добавляется ничего.
- Ошибка показывает, с чем именно пересечение: «Пересекается с записью 10.11 13:00–15:00 «обед»».

## Рассмотренные альтернативы
- **Разрешить пересечения и объединять при подсчёте** — статистика корректна, но журнал вводит в заблуждение, а пользователь не узнаёт об опечатке.
- **Автоматически обрезать/сливать записи** — неожиданное изменение пользовательских данных.
- **Уникальный индекс/триггер в SQLite** — пересечение интервалов через сутки неудобно выражать в SQL; логика в Core покрыта тестами и одинакова для всех сценариев.

## Последствия
- ➕ Статистика всегда честная; ошибка понятна и указывает на конфликтующую запись.
- ➖ Проверка выполняется в приложении, а не в БД: ручная правка файла БД может создать пересечение (приложение при этом продолжит работать и просто посчитает время дважды).
